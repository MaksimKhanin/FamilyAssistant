# Стенд: пройти панель снаружи и увидеть, чем это обернулось внутри

Стенд — служебный ход в панель, которым **сценарии проходят её так, как проходит
человек**, но с открытыми внутренностями: трейсами прогонов, предупреждениями
сервера, снимком базы и всеми обращениями к модели. Нужен он для одного:
пройти десяток пользовательских путей от и до, найти на них поломки и разобрать
каждую до причины, а не до «что-то не работает».

Тестам он не замена и не конкурент. Тест знает, что проверяет, и потому не
находит того, чего не ждал; стенд ходит целыми путями — «сказал → подтвердил →
открыл экран → дождался утренней сводки» — и ломается там, где расходятся куски,
каждый из которых по отдельности прав.

Код: [`app/testkit/`](../app/testkit/). Пульт: [`scripts/testkit.py`](../scripts/testkit.py).
Сценарии: [`scenarios/`](../scenarios/).

---

## 1. Включить

Стенд включается ключом и без ключа не существует: ни роутов, ни журнала, ни
подмены модели. Ключ короче двадцати знаков не принимается — ручки ходят мимо
входа и мимо ролей, и подобрать к ним ключ не должно быть проще, чем пароль.

```bash
export TESTKIT_TOKEN=$(python -c "import secrets; print(secrets.token_urlsafe(24))")
export TESTKIT_URL=http://127.0.0.1:8000

python run_local.py          # или uvicorn app.main:app
python scripts/testkit.py health
```

**В бою не включать.** `reset` сносит базу целиком, `login` пускает без пароля,
`state` показывает чужие строки. Стенд — для локального прогона и для отдельно
стоящей проверочной среды, где базы не жалко.

Без ключа настоящей модели стенд работает офлайн-разбором ключевых слов
(`app/agent/stub.py`) — этого хватает: что «решит» модель, сценарий обычно
говорит сам (см. режиссёра ниже).

## 2. Ручки

Все под `/api/testkit`, все за ключом — заголовком `X-Testkit-Token` или
параметром `token`. Заголовок `X-Testkit-Step` подписывает шаг: по нему потом
видно, чей это был запрос в журнале.

**Делать** — то же, что делает человек, только вызовом:

| Ручка | Что делает |
| --- | --- |
| `POST /reset` | сносит базу и собирает стенд заново (`confirm: "wipe"` обязателен) |
| `POST /login` | кука входа без пароля — дальше по экранам ходим обычным HTTP |
| `POST /say` | реплика ассистенту; в ответе реплика, инструменты, карточки, ждущие действия, трейс прогона, обращения к модели, предупреждения и стек, если упало |
| `POST /confirm` | «да» или «нет» на подготовленное действие |
| `POST /tool` | вызвать инструмент напрямую, минуя модель, — так готовят состояние |
| `POST /tick` | прогнать минуту расписаний с явным временем: сводки, напоминания, ротация |

**Смотреть** — что от этого стало:

| Ручка | Что показывает |
| --- | --- |
| `GET /state` | снимок базы глазами человека: `?user=marina&tables=meals,boards` |
| `GET /traces` | прогоны агента целиком: промпты, вызовы, токены, ошибки |
| `GET /requests` | журнал запросов: код, время, предупреждения, исключения, прогоны |
| `GET /messages` | что ассистент сказал сам — события шины, из которых растут push |
| `GET /model/calls` | все обращения к модели, включая неподставленные |
| `GET /routes` | все адреса панели — для обхода экранов |
| `GET /cursor` | номер, после которого смотреть дальше |

**Подстраивать** — `POST /model/script`, очередь ответов модели на ближайшие ходы.

## 3. Режиссёр модели

Живая модель для проверки поведения не годится дважды: она разная от запуска к
запуску, и самое интересное в ассистенте — то, что случается редко. Отчиталась о
работе, не вызвав инструмента. Попросила инструмент, которого нет. Прислала
мусор в аргументах. Не ответила вовсе. Дождаться такого нельзя, а поставить —
можно:

```json
{
  "chat": [
    {"when": "суп", "tool": "log_meal", "arguments": {"text": "суп и салат"}},
    {"content": "Записала. Это оценка — поправьте, если что."},
    {"error": "Модель недоступна"}
  ],
  "json": [
    {"json": {"title": "Паста", "kcal": 780, "protein": 40, "fat": 24, "carbs": 95}}
  ]
}
```

* `when` — подстрока последней реплики человека; ответы с `when` ищутся по
  порядку, первый подошедший выигрывает. **Ответы без `when` ставьте последними**:
  такой подходит к любому ходу и закрывает собой все следующие.
* `keep` — не вынимать ответ из очереди: им отвечают на любой ход подряд.
* `tool` + `arguments` — короткая запись одного вызова; несколько — через `tool_calls`.
* `error` — модель не ответила; ассистент обязан остаться живым.
* `json` — вторая очередь: оценка блюда по фото и по описанию, разбор записи
  доски на величины.

Кончилась очередь — ход доигрывает то, что стояло бы и без режиссёра: живая
модель или офлайн-разбор. В `model/calls` у таких ходов `scripted: false`.

## 4. Сценарии

Сценарий — файл YAML: известная база, очередь ответов модели, шаги и проверки.
Прогон складывает полный журнал в `.local/scenarios/<имя>.json` — с репликами,
вызовами, снимками, предупреждениями и записью о каждом запросе.

```bash
python scripts/testkit.py run scenarios/nutrition-day.yaml
python scripts/testkit.py run scenarios/*.yaml
```

```yaml
name: День питания
user: marina
reset: {autonomy: 2}          # autonomy: 0 — «всё спрашивает», 3 — «максимально сам»

model:
  chat: [{when: "суп", tool: log_meal, arguments: {text: "суп и салат"}}]

steps:
  - name: записал приём пищи словами
    say: "съел суп и салат"
    expect:
      tool: log_meal
      rows: [{table: meals, min: 2, contains: "суп"}]

  - name: экран показывает записанное
    open: /nutrition/meal
    expect: {status: 200, text_contains: "суп"}
```

**Шаги.** `say` (реплика, можно с `image_b64`), `open` (экран), `post` (действие
на экране: `data:` — поля формы), `confirm` (`approve` / `reject`), `tool`
(инструмент напрямую), `tick` (минута расписаний), `state` (снимок).
`user:` в шаге переключает, за кого идём; `user: anon` — никем, вход и
приглашение открываются без входа. `model:` внутри шага меняет очередь ответов
модели на ходу.

**Проверки** (`expect`): `reply_contains` / `reply_not_contains`, `tool`,
`no_tools`, `status`, `text_contains` / `text_not_contains`, `pending`,
`messages_contain`, `no_warnings` и `rows` — строки в базе:
`{table, min, max, contains, user}`. Упавший ход отмечается всегда, даже без
единой проверки.

**Значения, которые рождаются по ходу** — код приглашения, номер записи:

```yaml
  - post: /settings/accounts/member
    data: {display_name: "Соня", username: "sonya"}
    capture:
      code: {table: users, where: {username: sonya}, column: invite_code}
  - post: /invite/${code}
    user: anon
    data: {password: "sonya12345", password_repeat: "sonya12345"}
```

## 5. Пайплайн разбора

Так стендом и пользуются, когда ищут поломки:

1. **Пройти пути.** `python scripts/testkit.py run scenarios/*.yaml`. Каждый
   сценарий начинается с `reset`, поэтому прогоны не мешают друг другу.
2. **Обойти экраны.** `python scripts/testkit.py crawl marina` и то же за
   администратора: ищутся не тексты, а обвалы и заслоны не на своём месте.
3. **Прочитать журнал.** `python scripts/testkit.py requests --bad` — запросы с
   ошибкой, предупреждением или исключением. Предупреждение сервера («модель
   отчиталась о работе, которой не было») чаще всего и есть найденная поломка.
4. **Дойти до причины.** `traces --run N` показывает, что ушло в модель и что
   вернулось; `calls` — то же, когда трейсы выключены; `state` — что стало с
   данными. Этих трёх обычно хватает, чтобы назвать причину, а не симптом.
5. **Записать находку** issue в трекер (см. [issue-tracker](agents/issue-tracker.md))
   и **закрепить сценарием**: путь, на котором она вылезла, остаётся в
   `scenarios/` и проходится следующим прогоном.

Найденное, но не починенное, живёт в трекере, а не в голове: сценарий
проверяет, что поломка ещё на месте, ровно до того дня, когда её починят.
