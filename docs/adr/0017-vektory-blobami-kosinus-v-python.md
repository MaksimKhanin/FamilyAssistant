# Векторы — блобами в обычной таблице, косинус — в Python

`recall` искал только подстрокой (`ILIKE`): «грибы» не находили «шампиньоны».
Для поиска по смыслу нужны эмбеддинги — и первый вопрос был, где их хранить и
кто считает близость.

## Решение

- Таблица `board_entry_embeddings(entry_id, model, vector BLOB, updated_at)`:
  вектор — упакованный float32 (`app/core/embeddings.py: pack/unpack`).
- Близость — косинус **в Python** полным перебором доступных записей.
- Эмбеддер — OpenAI-совместимый `/embeddings` тем же голым-HTTP стилем, что
  озвучка; ручки `EMBED_MODEL` / `EMBED_BASE_URL` / `EMBED_API_KEY`. Не задан —
  recall остаётся чистым ILIKE, бит-в-бит прежним.
- Гибрид: подстрочные совпадения первыми (им веры больше), недобор до limit
  добивается топом по косинусу с порогом `SEMANTIC_THRESHOLD`.
- Индексация: best-effort при создании/правке записи плюс догоняющий backfill
  пачками в тике планировщика.

## Почему не pgvector / sqlite-vec

Корпус семьи маленький по построению: у досок капы (заметки — 50, итоги — 20,
правила — 20), а живая семья пишет сотни, не десятки тысяч записей. Полный
перебор такого корпуса — миллисекунды; нативные расширения дали бы двойную
ветку кода (SQLite и Postgres расширяются по-разному), заботу о деплое и ничего
взамен.

**Порог пересмотра:** если у семьи наберётся порядка 10 000 записей с
векторами, перебор в Python перестанет быть бесплатным — тогда возвращаемся к
этому решению с pgvector (и sqlite-vec для локального запуска) или с кешем
векторов в памяти процесса.
