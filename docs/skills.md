# Скиллы: кто выбирает нужный и что из этого работает на локальной модели

Документ отвечает на два вопроса, которые обычно задают вместе:

1. Как переиспользовать чужие скиллы у себя, чтобы ничего не качалось в момент обращения.
2. Как сделать, чтобы нужный скилл выбирался **сам**.

Короткий ответ на второй: отдельного «движка выбора» не существует — ни у Claude
Code, ни у кого-либо ещё. Выбор делает сама модель обычным вызовом инструмента,
по коротким описаниям, которые постоянно висят в контексте. И этот механизм в
нашем ассистенте **уже написан** — он в [`app/agent/registry.py`](../app/agent/registry.py)
и [`app/agent/llm.py`](../app/agent/llm.py). Ниже — из чего он состоит, как
ложится на наш код и что в нём ломается, когда думает не облачная модель, а
локальная восьмимиллиардная.

---

## 1. Что такое скилл

Папка с файлом `SKILL.md`. Всё.

```
research/
└── SKILL.md
```

```markdown
---
name: research
description: Investigate a question against high-trust primary sources and capture
  the findings as a Markdown file in the repo. Use when the user wants a topic
  researched, docs or API facts gathered, or reading legwork delegated.
---

Spin up a background agent to do the research, so you keep working while it reads.
...
```

Живой пример лежит прямо в этом репозитории:
[`.claude/skills/research/SKILL.md`](../.claude/skills/research/SKILL.md).

Не плагин, не код, не векторная база, не индекс. Заголовок из двух полей и текст
инструкции ниже. Скилл может нести рядом `references/` и `scripts/`, но
обязателен только `SKILL.md`.

---

## 2. Три уровня подгрузки — на них держится всё

```
всегда в контексте  ──▶  name + description        ~десятки токенов на скилл
                              │
                    модель выбрала скилл
                              ▼
читается по выбору  ──▶  тело SKILL.md             сотни–тысячи токенов
                              │
                    в теле ссылка на файл
                              ▼
читается по ссылке  ──▶  references/, scripts/     сколько угодно
```

| Уровень | Что грузится | Когда |
|---|---|---|
| 1 | только `name` и `description` каждого скилла | всегда, при старте сессии |
| 2 | тело `SKILL.md` | когда модель выбрала этот скилл |
| 3 | `references/`, `scripts/` | по ссылке из тела |

Смысл разделения: описаний может быть много, потому что они дёшевы; инструкций
может быть много, потому что они не грузятся, пока не нужны.

---

## 3. Кто и как делает выбор

Выбирает модель. Технически это **обычный вызов инструмента**: у неё есть
инструмент «запустить скилл», у которого в перечислении значений — имена всех
скиллов с их описаниями. Модель читает запрос человека, читает описания и
называет одно имя. Ровно то же самое, что делает наш ассистент, когда выбирает
между `log_meal` и `confirm_meal`.

Отсюда четыре следствия, и они важнее всей остальной механики:

**`description` — единственный вход в скилл.** Тело `SKILL.md` на выбор не влияет
вообще: пока скилл не выбран, его текст никто не читал. Можно написать
гениальную инструкцию, и она никогда не запустится, если описание не совпадает с
тем, как человек формулирует задачу.

**Чужое описание почти всегда надо переписывать.** Скилл из чужого репозитория
описан словами того проекта. Если у вас так не говорят — он не сработает.

**Автовыбор можно выключить, и это не полумера.** Строка
`disable-model-invocation: true` во фронтматтере убирает описание из видимости
модели совсем: скилл вызывается только руками, через `/имя`, зато не стоит
**ничего** в контексте. Плата — человек сам должен помнить, что скилл есть.
Так сделаны 14 из наших 24 завендоренных скиллов, включая
[`ask-matt`](../.claude/skills/ask-matt/SKILL.md) — он роутер по остальным, ему
незачем срабатывать самому. Разбор этого выбора у автора набора —
[`writing-for-agents/SKILL-MECHANICS.md`](../.claude/skills/writing-for-agents/SKILL-MECHANICS.md).

**«Без скачивания в моменте» получается само.** Файлы лежат в клоне
репозитория, читаются с диска. Сеть не нужна ни при выборе, ни при запуске.
Именно поэтому у нас завендорены 24 скилла в `.claude/skills/`, а не подключён
плагин — подробности в [`VENDORED.md`](../.claude/skills/VENDORED.md) и
[`claude-code-cloud.md`](./claude-code-cloud.md).

## 4. Откуда берут чужие скиллы

Справочно, если понадобится.

- **`VoltAgent/awesome-agent-skills`** — каталог, в нём **только README со
  ссылками** (~1500 позиций), файлов скиллов нет. Реюз = пройти по ссылке в
  апстрим-репозиторий и скопировать оттуда папку.
- **`anthropics/skills`** — настоящие 17 скиллов плюс `marketplace.json`.
- Процедура копирования у нас уже описана и проверена в
  [`VENDORED.md`](../.claude/skills/VENDORED.md); для нового источника меняются
  только URL и список папок.

Две ловушки при копировании: не заводить скилл с именем встроенной команды
(у нас на этом уже споткнулся `code-review` — см. `VENDORED.md`) и помнить, что
каждый добавленный скилл висит в контексте **каждой** сессии, даже когда не
нужен.

## 5. Как то же самое уже устроено в нашем ассистенте

Это ключевая часть. Механизм скиллов — не что-то новое, что предстоит построить.
Это то, что в [`app/agent`](../app/agent) работает с первого дня, просто под
другими именами:

| В Claude Code | В нашем коде |
|---|---|
| фронтматтер `description` | `ToolSpec.description` — [`registry.py`](../app/agent/registry.py) |
| список скиллов в контексте | `payload["tools"]` + `tool_choice: "auto"` — [`llm.py`](../app/agent/llm.py) |
| модель назвала скилл | `LLMResponse.tool_calls` — там же |
| скилл виден не всем | `ToolSpec.module` + `policy.available_tools()` — [`policy.py`](../app/agent/policy.py) |
| разрешение на запуск | `auto_from` и ползунок самостоятельности |
| подгрузка текста по надобности | `meal_rules` в [`prompts.py`](../app/agent/prompts.py) и `boards_prompt` в [`runtime.py`](../app/agent/runtime.py) |

Последняя строка — самая интересная. **Уровень 2 у нас уже есть.** Правило про
еду попадает в системный промпт, только если у человека включён модуль
`nutrition`; названия досок — только если включена `memory`. Это ровно
progressive disclosure: текст подгружается тогда, когда он нужен, и не занимает
контекст остальным.

Разница со скиллами одна: у нас триггер — **включённый модуль**, а у скиллов —
**смысл фразы**. Всё остальное совпадает.

Наши описания инструментов, кстати, уже написаны как хорошие описания скиллов —
по-русски, с разведением похожих случаев:

> Удалить ошибочную запись о еде: человек записал не то, продиктовал дважды или
> передумал. […] **Не путай с исправлением: если человек уточняет блюдо или вес,
> это confirm_meal.**
>
> — `delete_meal`, [`app/modules/nutrition/tools.py`](../app/modules/nutrition/tools.py)

Последняя фраза — не документация для человека. Это разграничитель для модели,
которая выбирает между двумя соседними инструментами. В скиллах пишут точно так же.

### Чем был бы скилл в нашей архитектуре

Инструментом `load_skill(name)`, который:

- зарегистрирован через `@tool` с `read_only=True` — значит `auto_from=0`,
  подтверждения не требует (см. таблицу в [`agent.md`](./agent.md));
- читает markdown с диска и возвращает его текст как `ToolResult.summary`;
- на этом заканчивается — дальше модель работает по полученной инструкции,
  вызывая обычные инструменты.

То есть скилл — это инструмент, возвращающий не результат действия, а **текст
инструкции**. Больше ничего в нём нет.

## 6. Что меняется, когда думает локальная модель

Наш `LLMClient` намеренно говорит по голому HTTP с OpenAI-совместимым endpoint'ом,
чтобы одинаково работать с Ollama, vLLM, LM Studio и облаком. Но одинаково
работает **транспорт**, а не качество выбора. Шесть вещей, о которых стоит знать
заранее.

### 6.1. Умеет ли ваш сервер `tools`

Не все связки модель + шаблон поддерживают function calling, и часть серверов
принимает поле `tools` молча, ничего с ним не делая. Симптом: модель отвечает
текстом «сейчас запишу», а `tool_calls` пустой.

Проверка — трейс: [`tracing.py`](../app/agent/tracing.py) пишет и отправленный
запрос, и полученный ответ целиком.

Обходной путь у нас уже написан: `json_completion()` + `_parse_json_object()` в
[`llm.py`](../app/agent/llm.py). Модель просят вернуть `{"skill": "имя"}` обычным
текстом, а парсер терпит и ```json-заборы, и лишнюю прозу вокруг. Для роутинга
этого достаточно.

### 6.2. Сколько кандидатов модель реально различает

Оценка, не измерение: 8B уверенно выбирает из **единиц** описаний, на трёх
десятках похожих начинает промахиваться. У Claude Code их больше сорока — но там
и модель другого класса.

Практический вывод: для локальной модели набор должен быть **коротким и
непересекающимся**. Два скилла с близкими описаниями хуже, чем один с широким.
У нас сейчас 19 инструментов на три модуля, но конкретному человеку видна только
часть — те, чьи модули включены. Это и есть основной способ держать список
коротким, и его же надо распространить на скиллы.

### 6.3. Бюджет контекста

Уровень 1 дёшев: десятки токенов на скилл, два-три десятка скиллов — около
тысячи токенов. Терпимо даже на маленьком окне.

Опасен уровень 2. Тело скилла на несколько тысяч токенов у модели с окном 8к
съедает заметную долю окна — вместе с системным промптом, историей на
`HISTORY_LIMIT = 16` сообщений и результатами инструментов. Для локальной модели
инструкцию надо держать короче, чем принято в чужих скиллах, написанных под
большое окно.

### 6.4. Язык описаний

Семья пишет по-русски — описания скиллов держать по-русски. Совпадение языка
запроса и описания заметно помогает выбору, особенно у небольших моделей. Все
`description` в `app/modules/*/tools.py` уже написаны по-русски, эту линию и
продолжать.

### 6.5. Размышление при выборе — выключено

Уже сделано и обосновано в коде: `LLM_REASONING=off` для чата, отдельный
`LLM_REASONING_ESTIMATE` для оценки КБЖУ. Выбор инструмента — не та работа, ради
которой стоит платить сотнями токенов размышления; оценка веса порции — та.

Напоминание из комментария в [`llm.py`](../app/agent/llm.py): «принял и
проигнорировал» — обычное поведение провайдера, проверять надо не кодом ответа,
а `usage.completion_tokens`.

### 6.6. Если скиллов станет много — двухступенчатый выбор

Запасной вариант, не первый шаг. Сначала дешёвый вызов «какая это тема», затем в
`tools` кладутся только скиллы этой темы. Стоит одного лишнего похода к модели и
усложняет трейсы, поэтому имеет смысл, только когда одноступенчатый выбор
измеримо промахивается (как это измерить — раздел 8).

## 7. Рецепт, если решим делать

Ничего из этого пока не сделано — это план на случай, если понадобится.

1. **Хранилище.** Каталог `skills/` в корне репозитория, по папке на скилл, в
   каждой `SKILL.md` с тем же фронтматтером. Не `.claude/skills/` — там скиллы
   для агента, который пишет код, а это разные наборы с разной судьбой.
2. **Индекс при старте.** Разобрать фронтматтеры один раз при подъёме приложения,
   сложить в словарь `name → (description, путь)`. Тела не читать.
3. **Инструмент.** Зарегистрировать `load_skill` через `@tool` с
   `read_only=True`, положив в `parameters` перечисление имён из индекса и
   собрав описание из описаний скиллов. Модуль — `core` или свой, чтобы работал
   фильтр из `policy.available_tools()`.
4. **Промпт.** Одна строка в `TOOLS_RULES` ([`prompts.py`](../app/agent/prompts.py)):
   когда браться за инструкцию, а когда отвечать сразу.
5. **Ограничение набора.** Тот же фильтр по модулям человека, что и у остальных
   инструментов, — иначе список кандидатов вырастет у всех сразу.
6. **Трейс.** Убедиться, что выбор скилла виден в «Что агент делал» так же, как
   вызов любого другого инструмента: без этого отладка вслепую.

## 8. Как проверить, что автовыбор работает

- **`LLM_STUB=1`** ([`stub.py`](../app/agent/stub.py)) — прогнать логику без
  модели вообще.
- **Трейсы** ([`tracing.py`](../app/agent/tracing.py)) — видно, какой набор
  `tools` ушёл и что модель выбрала в ответ.
- **Честная метрика.** Список из 15–20 настоящих фраз, какими семья пишет
  ассистенту, и доля правильных выборов на нём. После каждой правки описания —
  прогнать заново.

Последний пункт не формальность. Описание — единственный рычаг, влияющий на
выбор, и правится оно на ощупь. Без списка фраз «я улучшил описание» означает
«я поменял описание и не знаю, стало лучше или хуже».

---

## 9. Что не переносится из Claude Code

**Сканирование папок.** Claude Code сам обходит `.claude/skills` при старте.
Наш сервер так не умеет и уметь не должен по волшебству — это шаг 2 из рецепта,
обычный код.

**`scripts/` внутри скиллов.** У Claude Code есть Bash, поэтому скилл может
принести с собой программу и попросить её запустить. У семейного ассистента
исполнителя произвольных команд нет, и заводить его не надо: у нас инструменты с
объявленной схемой, политикой и записью в `action_log`. Скилл в нашей
архитектуре — только текст.

**Слэш-команды.** `/имя-скилла` — это интерфейс Claude Code. В чате ассистента
эквивалента нет и не нужно: человек пишет обычной фразой, в этом весь смысл.

## Итог одним абзацем

Скилл — это markdown-инструкция с двухстрочным заголовком. В контексте всегда
висят только заголовки; выбирает между ними сама модель обычным вызовом
инструмента; тело читается уже после выбора. Механизм у нас есть — это
`registry.py` плюс `tool_choice: "auto"`, и подгрузка по надобности тоже есть
(`meal_rules`, `boards_prompt`), только по включённому модулю, а не по смыслу
фразы. Что действительно потребует внимания на локальной модели — это не
механика, а **дисциплина описаний**: коротких, по-русски, непересекающихся, и
проверяемых на списке настоящих фраз.
